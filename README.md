# CacheWise — CPU Cache Locality Benchmark

CacheWise is a C++17 benchmarking project that investigates how memory-access patterns affect execution time. It compares row-wise and column-wise traversal of a contiguous matrix to study the performance implications of memory layout and spatial locality.

## Overview

Modern processors use a hierarchy of caches to reduce the time required to access data in main memory. Programs that access nearby memory locations consecutively can often make better use of cache lines than programs that repeatedly jump between distant locations.

CacheWise demonstrates this concept by traversing the same matrix in two different orders while checking that both approaches compute the same sum.

**Project goals**
- Compare row-wise and column-wise memory-access patterns.
- Measure execution time across multiple matrix sizes.
- Use warm-up runs and repeated trials to improve measurement reliability.
- Calculate average and median execution times.
- Export benchmark results to CSV and visualize performance with Python.

## How It Works

The matrix is represented by a `std::vector<double>`, which stores its elements contiguously in memory.

For an `N × N` matrix, the element at row `i` and column `j` is accessed using:

`matrix[i * N + j]`

### Row-wise traversal

The inner loop accesses consecutive elements in memory. This pattern takes advantage of spatial locality and can use the data brought into each cache line efficiently.

### Column-wise traversal

The inner loop advances between rows, jumping `N` elements at a time. For sufficiently large matrices, this strided access pattern can make less efficient use of cache lines.

The benchmark measures execution time to investigate these effects. It does not directly count cache misses.

## Getting Started

### Prerequisites

- A C++ compiler supporting C++17, such as GCC
- Python 3
- Matplotlib

### Compile and run

On Windows PowerShell, from the project directory:

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic -O2 cachewise.cpp -o cachewise.exe
.\cachewise.exe
```

The benchmark tests matrix dimensions of 128, 256, 512, 1024, and 2048, with seven measured trials per traversal method and matrix size.

The program checks that the two traversal methods produce matching sums and writes timing statistics to `results.csv`.

### Generate plots

Install Matplotlib if necessary:

```powershell
python -m pip install matplotlib
```

Run the plotting script:

```powershell
python plot_results.py
```

The script generates:
- `benchmark_results.png` — average execution time by matrix size.
- `performance_ratio.png` — column-wise execution time divided by row-wise execution time.

### Observations

- The smallest matrices showed little difference between traversal orders.
- For larger matrices, column-wise traversal took substantially longer in these experiments.
- The measured difference varied with matrix size and compiler optimization level.
- Repeated measurements, including both averages and medians, help reveal timing variability.

These measurements are specific to the environment in which the program was run. They should not be treated as universal performance guarantees.

## Benchmark Methodology

1. Allocate and initialize the matrix outside the timed region.
2. Execute both traversal methods as warm-up runs.
3. Measure each method over seven trials.
4. Alternate the measurement order between trials to reduce systematic ordering bias.
5. Check that the calculated sums match.
6. Calculate average and median execution times.
7. Export the measurements and traversal-time ratio to CSV.

The benchmark uses `-O0` and `-O2` builds for a comparative experiment. Compiler optimization, processor architecture, cache hierarchy, operating-system activity, and system load can all influence the results.

## Limitations

- Execution time is an indirect indicator of memory-access performance; the program does not directly measure cache hits or misses.
- Warm-up runs do not guarantee a fully warmed cache or a controlled cache state.
- Timing results can vary between runs and should be interpreted as experimental observations.
- The matrix benchmark does not simulate secondary-storage access or implement a software cache.
